## 🎯 Принципы хороших требований

### 1. INVEST Критерии
Каждое требование должно быть:
- **I**ndependent (Независимым) - можно реализовать отдельно
- **N**egotiable (Переговорным) - детали обсуждаемы
- **V**aluable (Ценным) - приносит бизнес-ценность
- **E**stimable (Оцениваемым) - можно оценить сложность
- **S**mall (Малым) - помещается в одну итерацию
- **T**estable (Тестируемым) - можно написать тест

### 2. Атомарность
**Правило:** Один файл = одно требование

❌ **ПЛОХО** (супертребование):
```markdown
# REQ-001: Управление пользователями и аутентификация
- Регистрация пользователей
- Вход в систему
- Восстановление пароля
- Профиль пользователя
- Роли и permissions
```

✅ **ХОРОШО** (атомарные требования):
```markdown
# REQ-001: Регистрация пользователя через email
# REQ-002: Аутентификация по логину и паролю
# REQ-003: Восстановление пароля через email
# REQ-004: Просмотр профиля пользователя
# REQ-005: Назначение ролей пользователю
```

### 3. Структура требования

```yaml
---
id: REQ-001
title: Регистрация пользователя через email
status: draft  # draft | review | approved | implemented | rejected
priority: high  # low | medium | high | critical
iteration: 1    # номер итерации для реализации
created: 2024-01-15
updated: 2024-01-15
author: analyst-agent
related:
  - depends-on: []
  - conflicts-with: []
  - refines: []
  - split-from: []
tags: [authentication, user-management]
---

## Бизнес-ценность
Позволяет новым пользователям создавать учетную запись...

## Функциональные требования
1. Система должна предоставлять форму регистрации...
2. Система должна отправлять подтверждение на email...

## Нефункциональные требования
1. Время обработки запроса ≤ 2 секунд
2. Поддержка минимум 100 регистраций в минуту

## Критерии приемки (Acceptance Criteria)

### AC-1: Успешная регистрация
**Given:** Пользователь находится на странице регистрации
**When:** Пользователь вводит корректный email и пароль
**Then:** 
- Аккаунт создается в системе
- Отправляется письмо с подтверждением
- Пользователь перенаправляется на страницу подтверждения

### AC-2: Недопустимый email
**Given:** Пользователь находится на странице регистрации
**When:** Пользователь вводит email без @
**Then:** 
- Отображается ошибка "Некорректный email"
- Аккаунт не создается

### AC-3: Слабый пароль
**Given:** Пользователь находится на странице регистрации
**When:** Пользователь вводит пароль короче 8 символов
**Then:**
- Отображается ошибка "Пароль должен содержать минимум 8 символов"
- Аккаунт не создается

## Глоссарий
- **Email** - уникальный идентификатор пользователя в формате RFC 5322
- **Пароль** - секретная строка для аутентификации
```

### 4. Связи между требованиями

#### Типы связей
| Тип | Описание | Пример |
|-----|----------|--------|
| `depends-on` | Требует реализации другого требования | Регистрация зависит от хранения пользователей |
| `conflicts-with` | Противоречит другому требованию | Два разных подхода к аутентификации |
| `refines` | Уточняет другое требование | Детализация общего требования |
| `split-from` | Разделено из другого требования | Большое требование разделено на части |

#### Правила связывания
- ✅ Все связи должны быть двусторонне согласованы
- ✅ Не должно быть циклических зависимостей
- ✅ Если A depends-on B, то B должна существовать
- ⚠️ Избегать чрезмерного связывания (max 3-5 связей на требование)

### 5. Критерии приемки (Acceptance Criteria)

#### Формат Given-When-Then
```gherkin
Given [контекст/предусловие]
When [действие]
Then [ожидаемый результат]
```

#### Правила написания AC
- ✅ Каждый AC независим и тестируем
- ✅ Используется язык бизнеса (Ubiquitous Language)
- ✅ Избегать технических деталей реализации
- ✅ Покрывать как happy path, так и edge cases
- ✅ Минимум 3 AC на требование (happy + 2 edge cases)

#### Примеры хороших AC
```gherkin
# ✅ Хорошо - проверяет поведение
Given пользователь авторизован
When пользователь добавляет товар в корзину
Then товар отображается в корзине
And общая сумма корзины увеличивается на цену товара

# ❌ Плохо - проверяет реализацию
Given пользователь на странице товара
When пользователь кликает кнопку "Добавить"
Then вызывается метод Cart.add()
```

### 6. Нефункциональные требования

#### Категории NFR
| Категория | Примеры метрик |
|-----------|---------------|
| Производительность | Время ответа, throughput, latency |
| Масштабируемость | Количество пользователей, RPS |
| Надежность | Uptime, MTBF, MTTR |
| Безопасность | AuthZ/AuthN, шифрование, аудит |
| Удобство использования | Время обучения, error rate |
| Совместимость | Браузеры, ОС, версии API |

#### Примеры хороших NFR
```markdown
✅ Производительность:
- 95% запросов обрабатываются быстрее 200ms
- Система поддерживает 1000 одновременных пользователей

✅ Надежность:
- Доступность 99.9% (менее 9 часов простоя в год)
- Восстановление после сбоя за 5 минут

✅ Безопасность:
- Все пароли хешируются алгоритмом Argon2
- JWT токены истекают через 15 минут
```

### 7. Распространенные ошибки

| Ошибка | Как исправить |
|--------|---------------|
| "Супертребование" | Разделить на атомарные части |
| Технические детали | Удалить, оставить только "что", а не "как" |
| Нет критериев приемки | Добавить 3+ AC в формате GWT |
| Неявные зависимости | Явно указать в `related.depends-on` |
| Непроверяемые требования | Добавить измеримые критерии |
| Смешение функциональных и нефункциональных | Разделить на отдельные секции |

### 8. Чеклист качества требования

Перед отправкой на ревью проверить:
- [ ] Требование атомарно (не супертребование)
- [ ] ID уникален и соответствует формату
- [ ] Название отражает бизнес-ценность
- [ ] Бизнес-ценность явно описана
- [ ] Есть минимум 3 критерия приемки
- [ ] Критерии в формате Given-When-Then
- [ ] Есть нефункциональные требования (если применимо)
- [ ] Связи указаны корректно
- [ ] Термины из глоссария используются
- [ ] Нет технических деталей реализации
- [ ] Требование тестируемо
- [ ] Требование оцениваемо по сложности
